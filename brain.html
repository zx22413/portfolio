TL;DR

  • 產出：從 Brain 抽出 5 個 獨立 OSS 模組（forget-rag、mcp-fts5-starter 等）。

01 系統架構

Brain 不是 demo，是我每天在用的東西。要讓它天天在跑，必須做到三件事：多入口（手機、桌機、Claude Code session 都進得來）、單一真相（vault + SQLite 是唯一真相來源，其他都是衍生視圖）、以及不會壞（cron + GitHub Actions 是骨幹，real-time push 是奢侈品）。

三層架構 — Entry / Core / Storage + 橫切監控

三個入口都直連核心層，不經過彼此。這是設計選擇，不是巧合——任何一個入口掛了，其他兩個還能用。天天在跑的系統最怕單點失敗，因為單點失敗會逼你開電腦修，而開電腦修這件事本身就是「天天在跑」的反義詞。

02 5 個關鍵設計選擇

這 5 個選擇是 Brain 跟「另一個 RAG demo」差最多的地方。每一個都是取捨，每一個都在 2 個月的天天運作中真的被驗證過。

Choice 01

為什麼 SQLite + FTS5 而非向量資料庫？

啟動成本低、樹莓派跑得動、不用 docker compose 起 4 個服務。FTS5 解 80% 的搜尋場景。剩下 20% 才接 Gemini embeddings 做混合搜尋。決策原則：「先從跑得動的最簡單方案開始」。如果有一天 SQLite 撐不住了，那是個好問題——但還沒到那一天。

Choice 02

為什麼 熱度衰減 + 三層儲存 而非無限保留？

Brain 跑 2 個月，舊筆記變雜訊。RAG 撈到 2024 年的舊草稿打斷正在做的事。L1（熱）/ L2（溫）/ L3（歸檔）不刪除舊資料，只是讓 RAG 預設只看 L1+L2。能不能搜到 L3 由使用者明確指定。上線中的知識系統，合理的預設是「最近的最重要」，不是「全部都重要」。這個模組後來抽出來變成 forget-rag。

Choice 03

為什麼 TG Bot 是主入口而非 Web UI？

我在哪、Bot 在哪。手機上、辦公室、家裡——同一個對話視窗。Web UI 要設計 UX、處理 session、做認證；Bot 直接用 Telegram 的基礎建設，省 90% 工。代價是一次只能服務我一個人——但 Brain 本來就是私人系統。當需求是天天在用的個人生產力工具，從工程量回推入口設計才對。

Choice 04

為什麼 cron 排程 而非 real-time push？

日報 / 週報 / 維護任務全是 cron。即時推送要處理 backpressure / retry / dead letter queue，cron 只要失敗重試就好。出錯面積差一個數量級。代價是延遲——但個人知識系統不需要毫秒級回應，需要的是不會壞。Brain 上線 2 個月，cron 任務的恢復成本接近零；real-time push 一壞就要花一整個下午查佇列。

Choice 05

為什麼上線 MCP 監控但 14 天後砍計畫？

Phase 0 上線後稽核發現監控只抓到 0.22% 流量。沒救了——剩下 99.78% 走 Bot/REST 直呼核心，根本不過 MCP。當下我有兩個選擇：花一個月修監控架構，或承認假設錯、砍掉 Phase 1 的 BQML benchmark 計畫，把這次經驗寫成回顧文。我選後者。沉沒成本是最危險的反模式，14 天後的稽核就是設計來破除它的。

03 這個系統證明我能在 AI 新創做什麼

Portfolio 不是「給你看程式碼有多漂亮」，是把抽象能力翻譯成可驗證的主張。Brain 跑了 2 個月，下面三條是它證明的東西——每一條都有證據，不是行銷話術：

主張 01 設計上線級的 AI 基礎建設。 2 個月真的在跑，不是 demo。多入口、單一真相、cron 撐骨幹，從頭自己設計、自己上線、自己維護。
主張 02 在成本與複雜度之間取捨。 SQLite 不是漂亮的選擇，但是對的選擇。向量資料庫 / Kubernetes / 微服務都是「之後再說」的奢侈品；個人系統的合理預設是從最小開始。
主張 03 上線後願意稽核自己。 MCP 監控的回顧文就是證據。14 天後跑覆蓋率稽核、發現假設錯、砍掉自己的計畫——能砍掉自己的計畫比能寫程式更稀缺。
