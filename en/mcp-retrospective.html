MCP Monitoring: a 14-day audit killed my own plan.

I assumed instrumentation would cover all Brain traffic. Two weeks later, the data said I was wrong by ~450×.

TL;DR
  • Designed an anomaly-detection pipeline (instrumentation → store → detector → judge → alerter) to monitor Brain traffic.
  • 14-day audit found 0.22% coverage. Real traffic bypasses the MCP layer where the decorator lives — expected 30–60 events/day, got ~4.
  • Killed my own BQML benchmark plan, kept the cron (cost is zero), rewrote the project as a portfolio retrospective. Verifying assumptions beats defending them.

01 The hypothesis

The plan was clean on paper. Brain — my private knowledge system — speaks MCP. So if I wrap every MCP tool call in a tiny decorator that logs tool_name, args_hash, latency_ms, and status into a SQLite store, I should see the full pulse of the system. From there: a z-score detector for hourly anomalies, a Gemini-based judge to filter false positives, and a Telegram alerter for genuine spikes.

The implicit assumption — the one I never wrote down — was that MCP is the front door. That if traffic exists, it exists as MCP tool calls. I expected somewhere between 30 and 60 events per day after the modeling layer warmed up. Enough signal to do real work.

02 The build

Five small modules, each with one job. I deployed them to EC2 behind a 15-minute cron. The pipeline:

Pipeline — 5 modules, one cron

End-to-end latency was ~33ms per record. Health was easy to read: cron last-run timestamp, row count, judge call success rate. Everything green.

03 The deploy

Anomaly detection is statistically meaningless on a cold pipeline — small samples produce wild z-scores. So I gated readiness in three explicit stages, each with different behavior:

Cold start < 7 days Skip detection entirely. Just collect.
→
Warming 7–14 days Run detection, label outputs “tentative.” No alerts.
→
Ready ≥ 14 days Full pipeline. Alerts go live.

Day 14 came. Pipeline transitioned to READY. Cron kept firing every quarter-hour. Health checks all green. So I did what I should have done on day one and nobody — including past me — thought to do: I asked the obvious question.

Is the data we’re collecting actually the data we said we’d collect?

The pipeline was running. The pipeline was healthy. The pipeline was watching almost nothing.

99.78% of Brain’s real traffic doesn’t enter through MCP at all. It enters through the Telegram bot or through internal REST handlers that call core functions directly — bypassing the decorator layer where my instrumentation lives. The MCP front door is just one of three doors, and apparently the least-used one.

05 The attribution

Once the gap was visible, the next question was where exactly the leak sits. I have three live hypotheses; the root cause isn’t fully nailed down yet.

  • H1 Decorator not active on the running process. The instrumentation wraps an MCP-layer entry point. If the runtime imports the un-wrapped module first — Python import order is fragile — the decorator silently doesn’t apply. No error. No log line.
  • H2 GHA deploy didn’t reload the long-running service. CI ships new code, but the systemd unit on EC2 wasn’t restarted. New decorator code on disk, old process in memory. This bites until the next reboot.
  • H3 MCP traffic is genuinely low. Most Brain interaction goes through TG bot and REST. MCP is reserved for Claude Code sessions — rarer than I assumed. In which case “the monitor is fine, it’s just watching the quiet door.”
Narrowing this is straightforward — tail the systemd logs, ship a debug trace, recount — and worth a few hours. Not worth weeks of rebuilding the pipeline before knowing which of the three it is.

06 The decision

My original next step was a BQML TimesFM benchmark on the captured data — comparing zero-shot foundation models against my z-score baseline. With ~4 events/day the comparison is statistically meaningless. So I made three calls in the same hour:

× Kill BQML benchmark plan Sample size won’t support the comparison. No amount of model sophistication fixes that.
✓ Keep The cron, untouched Cost is effectively zero. Useful as a baseline if I fix instrumentation later.
→ Rewrite Project framing From “monitoring system that worked” to “monitoring system that taught me something.”

07 What I learned

Everything I built worked. The decorator runs in 33ms. The detector computes. The judge replies. The alerter delivers. Nothing in the pipeline is broken.

And it didn’t matter, because the assumption underneath was wrong, and nothing in my health checks would ever have told me. Health says “the machine is on.” Coverage says “the machine is pointed at the right thing.”

“
Auto systems must run a 14-day coverage audit, not just health checks. ‘It’s running’ ≠ ‘it’s working.’

The hardest move on a working system isn’t adding more — it’s asking whether what’s already there is pointed at reality. I now treat that as a hard 14-day deliverable on every automation I ship, alongside the build itself: a number, a verification date, and the willingness to kill the project if the number disagrees.

That last part is the only part that’s actually hard.
